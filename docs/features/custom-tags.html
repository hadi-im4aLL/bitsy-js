Custom tags

Every directive name is configurable. Pass the keys you want to rename in settings.tags; the keys you leave out keep their defaults.

The tags setting#

Every directive name lives in settings.tags. The library reads each directive out of the DOM using the string you provide, so changing a key changes the attribute or the custom tag that your markup has to use. The defaults are:

Tag configuration keys, their default values and what each one controls
Key Default What it controls
dataBind b-data Scope attribute. Placeholders only bind inside an element that carries it.
forLoop b-for Loop attribute.
conditionIf b-if Conditional attribute.
rawJs b-js Expression attribute that writes HTML.
view b-view Custom tag that fetches a fragment.
container b-container Custom tag that is unwrapped after rendering.
on b-on Attribute prefix for event bindings. The event name is everything after the colon, so renaming it to x-on turns b-on:click into x-on:click.
event b-event Base name for declarative events. The library builds data-${tags.event}, so x-event gives data-x-event, data-x-event-html, data-x-event-remote and every other modifier.
remoteData data-b-remote-data Full attribute name used inside a template. The default already contains the data-b- prefix.
useTemplate data-b-use-template Full attribute name that points a target at a <template>.
keepExisting data-b-keep-existing Full attribute name that appends instead of replacing.
validateForm data-b-validate-form Full attribute name that marks a form for validation.
validateRule data-b-validate Full attribute name that holds a field's rule list.
validateMessage data-b-validate-message Full attribute name that names the message slot for a field.
validateErrorMessage data-b-validate-error-message Full attribute name that overrides the message for one field.
formAjax data-b-form-ajax Full attribute name that switches a form to fetch submission.
formAjaxRender data-b-form-ajax-target Full attribute name that selects the response target.
formRemoveOnSubmit data-b-form-remove-on-submit Full attribute name that removes the form after a successful submit.
formIndicator data-b-form-indicator Full attribute name whose value is the loading class used during submit.
formConfirm data-b-form-confirm Full attribute name whose value is the confirmation message shown before submit.

Four keys are plain attribute names, two are custom tag names, on and event are turned into other names before use, and the remaining twelve are complete attribute names. The on and event keys are the two that expand into a whole family of attributes.

Partial merging#

The constructor merges settings.tags over the defaults key by key. Pass only the keys you want to change and every key you leave out keeps its default: 

import { BitsyJS } from "./bitsy.min.js";

const bitsy = new BitsyJS({
    tags: {
        on: "x-on",
    },
});

// Merged result:
// bitsy.settings.tags.on    -> "x-on"
// bitsy.settings.tags.dataBind -> "b-data"
// bitsy.settings.tags.event -> "b-event"

With that configuration b-on:click is no longer a directive, x-on:click is, and b-data, b-for, b-if, b-js, b-view, b-container and the whole data-b-* family keep working exactly as before.

Only the keys you pass change. A partial tags object is safe: the constructor spreads your keys over the defaults and every missing key keeps its default. You never need to repeat keys you are not renaming.

The merged object is available as bitsy.settings.tags after construction, and every internal module reads its names from it. bitsy.config.tags still holds the untouched defaults, so read settings.tags when you want to know what the instance actually uses. There is no method to change tags after construction; decide the vocabulary when you create the instance.

Renaming directives#

Renaming a directive is a two-part change: configure the key, then rewrite the markup that uses it. The library only ever looks for the configured string, so the old names become ordinary inert attributes.

Attribute names

dataBind, forLoop, conditionIf and rawJs are matched exactly:

<div x-data="{ open: true }">
    <p x-if="open">Visible</p>
    <span x-js="open ? 'yes' : 'no'"></span>
    <li x-for="item of items">{item.name}</li>
</div>

Event bindings

on is a prefix. Any attribute whose name starts with the configured prefix plus a colon is treated as a DOM event binding, and the rest of the name is passed to addEventListener. The attribute is removed after the listener is attached. 

<button type="button" x-on:click="count.update(n => n + 1)">+1</button>
<input type="text" x-on:input="name.set($event.target.value)" />

Declarative events

event is a base name. Every declarative attribute is built from it, so a single key allows you to rewrite the entire family:

  • data-b-event becomes data-x-event.
  • data-b-event-html, -text, -add-class, -remove-class, -toggle-class, -remote, -target, -indicator, -confirm, -revert, -remote-method and -remote-payload all become data-x-event-*. 
<button
    type="button"
    data-x-event="click"
    data-x-event-html="<strong>Saved</strong>"
    data-x-event-revert="2s">
    Save
</button>

The data-b-* families

Remote, template, validation and form keys are complete attribute names. They already contain the data-b- prefix, so a rename has to spell the whole new name, including its own prefix: 

<div id="users" data-x-use-template="#users-tpl" data-x-keep-existing></div>

<template id="users-tpl" data-x-remote-data="users">
    <li x-for="user of users">{user.name}</li>
</template>

<form data-x-validate-form="true" data-x-form-ajax="true" data-x-form-ajax-target="#result">
    <input name="email" data-x-validate="required|email" />
    <small data-x-validate-message="email"></small>
</form>

Here is the complete rename:

const bitsy = new BitsyJS({
    tags: {
        dataBind: "x-data",
        forLoop: "x-for",
        view: "x-view",
        container: "x-container",
        conditionIf: "x-if",
        rawJs: "x-js",
        on: "x-on",
        event: "x-event",
        remoteData: "data-x-remote-data",
        useTemplate: "data-x-use-template",
        keepExisting: "data-x-keep-existing",
        validateForm: "data-x-validate-form",
        validateRule: "data-x-validate",
        validateMessage: "data-x-validate-message",
        validateErrorMessage: "data-x-validate-error-message",
        formAjax: "data-x-form-ajax",
        formAjaxRender: "data-x-form-ajax-target",
        formRemoveOnSubmit: "data-x-form-remove-on-submit",
        formIndicator: "data-x-form-indicator",
        formConfirm: "data-x-form-confirm",
    },
});

    The x-* column is deliberately not inside a b-data element. A b-data scope binds every placeholder in its subtree, so putting the renamed block inside one would make instance 1 try to evaluate {team} against the wrong scope.

    Two sequential runs have one side effect worth knowing before you prerender a page like this: the ready signal fires at the end of the first run, so a snapshot can be taken between the two. The saved HTML then holds the default render and the raw x-* markup. The Lifecycle page describes the signal and how to plan around it. 

    import { BitsyJS } from "./bitsy.min.js";

// The default instance handles the b-* markup.
const defaults = new BitsyJS({ data: { greeting: "Handled by instance 1" } });
await defaults.run();

// A second instance handles only the renamed x-* markup.
const custom = new BitsyJS({
    tags: {
        dataBind: "x-data",
        forLoop: "x-for",
        view: "x-view",
        container: "x-container",
        conditionIf: "x-if",
        rawJs: "x-js",
        on: "x-on",
        event: "x-event",
        // the rest of the data-x-* keys as above
    },
});

await custom.run();

    Namespacing guidance#

    Renaming is worth the churn when the default vocabulary collides with something else: another HTML-first library that claims x-data, a CMS that strips unknown attributes, two independent BitsyJS instances on one page, or a team convention that wants one prefix for every directive.

    • Renaming is not scoping. Each instance scans the whole document on run(). Any element that uses its tags is processed, wherever it sits. Isolation comes from using different names, not from wrapping markup in a container.
    • One instance per vocabulary. Run each instance once. If you divide a page into regions, divide it by tag set, not by component.
    • Keep names valid. They are passed to querySelectorAll, getAttribute and addEventListener, so attribute and tag names must be valid, lowercase and free of characters that break a selector. The on value is used as an attribute prefix, followed by a colon and the event name.
    • Mind the fixed data-b- check. Placeholder binding skips attribute names that start with the literal data-b-. After renaming the declarative event family to data-x-event, those attributes are no longer skipped, so a declarative value that contains braces inside a b-data subtree is treated as a placeholder template and rewritten. Keep declarative values free of braces, or use b-on for those cases.
    • Template syntax follows the keys. A renamed template uses the renamed attribute names for b-for, b-if and the remote-data variable, because templates are rendered with the same instance configuration.

    The lifecycle of two instances is covered in Lifecycle, and the tags key is documented with the rest of the settings in API reference.
