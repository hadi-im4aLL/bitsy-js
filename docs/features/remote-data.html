Remote data and templates

Use data-b-event-remote to fetch a URL when an event fires. BitsyJS parses the response by content type and renders it into a target, optionally using a <template>.

Fetch on an event#

Set data-b-event to the event name and data-b-event-remote to the URL to fetch. Put both attributes on the same element. 

<button type="button"
    data-b-event="click"
    data-b-event-remote="../api/users.json"
    data-b-event-target="#user-list">
    Load users
</button>

<div id="user-list"></div>

The request uses GET unless data-b-event-remote-method overrides it. A non-2xx response rejects with an error that includes the status and response body. It does not update the target.

Target and loading class#

Set data-b-event-target to a CSS selector for the element that should receive the response. Without a matching target, BitsyJS still sends the request but does not render the response.

BitsyJS adds is--loading to the target while the request runs, or to the trigger if no target matches. Set data-b-event-indicator on the trigger to use a different class. 

<button type="button"
    data-b-event="click"
    data-b-event-remote="../api/report.html"
    data-b-event-target="#report"
    data-b-event-indicator="is--loading">
    Load the report
</button>
A failed request leaves the loading class in place. BitsyJS removes it only after a successful response is handled and does not catch the rejection. Use your own request handler if you need to show an error or clear the indicator on failure.

Response parsing#

The response is parsed by its Content-Type header:

  • A type containing json is parsed as JSON, which can return a scalar as well as an object or array.
  • A type containing html or starting with text/ is read as a string.
  • A type containing image/ is read as a Blob.
  • For other types, BitsyJS tries JSON.parse and keeps the original text if parsing fails.

Without a template, BitsyJS serializes objects and arrays with JSON.stringify(result, null, 2) and assigns the result to innerHTML. Strings go directly to innerHTML. Neither path escapes or sanitizes markup, so render only trusted responses. A Blob renders as {}; use your own handler to display it as an image.

Templates#

Give the target data-b-use-template="#id" and let the template name its data with data-b-remote-data. The name becomes a variable that the markup inside the template reads. 

<div id="user-list" data-b-use-template="#users-template"></div>

<template id="users-template" data-b-remote-data="users">
    <ul>
        <li b-for="user of users">
            {user.name} - {user.email}
        </li>
    </ul>
</template>

For a JSON array response the named variable holds the array, so b-for="user of users" repeats one row per user. b-for and b-if work inside a template, and the loop adds the usual _index, _isFirst and _isLast values. Rendering replaces the target's children, so a second fetch produces a fresh list.

A template also works for form responses: the same renderer is used by AJAX form submissions.

Scope inside a template#

The template starts with only the variable named by data-b-remote-data, not the constructor's data option. With an array named users, {users.length} resolves but {appName} stays as written.

BitsyJS substitutes placeholders in the original template before cloning it. Once {users.0.name} resolves, its value becomes part of that template and later renders reuse it. Directives in each clone can still evaluate against the latest response. 

<template id="users-template" data-b-remote-data="users">
    <!-- resolved on the first render only -->
    <p>First user: {users.0.name}</p>

    <!-- re-evaluated on every render -->
    <p b-for="user of users">{user.name}</p>
</template>
Use b-for for values that must refresh and b-if for conditions. In the example, {user.name} is bound for each row, and the loop rebuilds from the latest response.

Append with keep-existing#

Add data-b-keep-existing to a target that uses a template to append each rendered fragment instead of replacing the target's children. The attribute's presence is enough; its value is ignored. 

<button type="button"
    data-b-event="click"
    data-b-event-remote="../api/users.json"
    data-b-event-target="#stream">
    Load a page
</button>

<div id="stream" data-b-use-template="#row-template" data-b-keep-existing></div>

Every click adds another rendered block to the end of the target, which suits paged or accumulated lists. The template stays the source, so the appended block follows the same scope rules as the first one.

Method, payload and confirm#

Set the method with data-b-event-remote-method. For a method other than GET, data-b-event-remote-payload can supply a JSON body. BitsyJS parses and serializes the payload before sending it. An invalid payload stops the request before it is sent. 

<button type="button"
    data-b-event="click"
    data-b-event-remote="../api/users"
    data-b-event-remote-method="POST"
    data-b-event-remote-payload='{ "name": "Ada", "role": "Engineer" }'
    data-b-event-target="#user-list"
    data-b-event-confirm="Create this user?">
    Create user
</button>

The payload is ignored for GET, which has no body. data-b-event-confirm is checked before the request starts, so cancelling the dialog means no fetch at all; it is only read by the remote action.

What it does not do#

  • No cancellation or response ordering. Two quick clicks send two requests. With replacement, the last response rendered wins; with append, results appear in completion order.
  • No debounce or queueing. Each event starts its own request unless confirmation is canceled.
  • No policy for credentials, headers, retries or timeouts. The fetch uses browser defaults only.
  • No error rendering. A rejected request renders nothing and leaves the loading class in place, as described above.
  • Listeners are attached once during run(), and the data-b-event-* attributes stay in the DOM afterwards.
