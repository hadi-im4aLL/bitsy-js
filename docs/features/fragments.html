Fragments

<b-view> loads an HTML fragment. BitsyJS replaces the tag with the fetched markup before processing bindings and directives.

The b-view tag#

Use <b-view> with a src attribute pointing to the HTML file to load during run().

<section class="team">
    <b-view src="./partials/team.html"></b-view>
</section>

Top-level sources resolve against document.baseURI, which defaults to the page URL unless set by a <base> tag. Paths starting with / resolve from that base URL's origin; absolute URLs do not use the base.

Always write the closing tag. HTML has no self-closing syntax for custom elements, so <b-view src="./partials/team.html" /> is parsed as an open tag, the markup that follows becomes its child, and the replacement removes that child along with the tag.

The tag itself does not survive. The fetched nodes take its place as siblings, so a fragment with three root elements inserts three siblings, and any class, id or style written on the b-view tag is discarded with it. Wrap the tag in an element when the page needs a box around the fetched markup.

When fragments are fetched#

Fragment loading is the first step of run(), before any scope, binding or directive exists. The full order is fixed:

// inside run(), in this order
// fragment.bootstrap()    fetch every b-view, then inline all of them
// dataBind.bootstrap()    read b-data scopes and bind placeholders
// directive.bootstrap()   b-for, b-if, b-js
// container.flush()       unwrap b-container
// dataBind.flush()        remove the b-data attributes
// eventHandler.listen()   attach data-b-event and b-on listeners
// validate.bootstrap()    wire form validation

Once inserted, fragments can use scopes, directives, events and form attributes just like the surrounding markup.

BitsyJS loads top-level and nested fragments before inserting any of them. A <b-view> inside a b-if block or a b-for row template is fetched before the block is hidden or the rows are built.

Nested fragments#

A nested source resolves relative to the fragment file that contains it, not relative to the page. The base for a child is the URL of its parent fragment. 

<!-- assets/demo/team.html, {appName} needs a b-data ancestor -->
<div>
    <h3>{appName} team</h3>
    <ul>
        <li b-for="member of members()">
            <span>{member.name}</span>
            <b>{member.role}</b>
        </li>
    </ul>
    <div class="nested">
        <b-view src="./team-footer.html"></b-view>
    </div>
</div>

Here ./team-footer.html resolves next to team.html, at assets/demo/team-footer.html. Do not include a fragment in itself, directly or indirectly. BitsyJS does not detect cycles or limit nesting depth.

Fragments and scopes#

Inlined markup reads the scope of the page around it. A fragment placed inside a b-data element sees that element's keys, and every fragment sees the global data passed to the constructor. 

<!-- the page -->
<div b-data="{ status: 'ready' }">
    <b-view src="./partials/status.html"></b-view>
</div>

<!-- partials/status.html, no scope of its own -->
<p>Status: {status}</p>

The fragment has no scope of its own, so its placeholder binds against the enclosing b-data element on the page and renders ready. A fragment may also bring its own scope; that scope is parsed from the fragment's own attribute and does not inherit the local keys of the page around it. 

<!-- partials/card.html -->
<div b-data="{ heading: 'Fragment card', body: 'Fetched from another file.' }">
    <h3>{heading}</h3>
    <p>{body}</p>
</div>

The rules are exactly the ones that apply to inline markup: global data is always the base, a b-data adds its own keys, and a nested b-data replaces the local part instead of extending it. So a fragment that owns a b-data cannot read a key that only exists on the page's own b-data element.

Outside loop rows, text placeholders bind only within a b-data scope. Without one, {title} stays literal. Directives such as b-for, b-if and b-js can read constructor data without b-data.

A live fragment#

The block below is one real b-view pointing at assets/demo/team.html. The heading, the member loop and the nested footer all come from fragment files. The framed panel around the tag is page markup; everything inside it was fetched. The controls write to signals passed through the constructor, and the inlined bindings and loop update on their own.

One tag, two files live
assets/demo/team.html 2 files

Editing appName updates the heading. Adding or removing a member rebuilds the list without refetching either fragment. The footer is outside the list and stays in place.

The page supplies the panel wrapper and controls. The <b-view> tag supplies its contents:

<div b-data>
    <label>
        appName
        <input
            type="text"
            value="{appName()}"
            b-on:input="appName.set($event.target.value)"
        />
    </label>
    <button type="button" b-on:click="addMember()">Add member</button>
    <button type="button" b-on:click="removeMember()">Remove last</button>

    <div class="panel">
        <b-view src="../assets/demo/team.html"></b-view>
    </div>
</div>

The fetched file is plain page markup as well, with one nested tag of its own:

<!-- assets/demo/team.html -->
<div>
    <h3>{appName} team</h3>
    <span>{members().length} members</span>

    <ul>
        <li b-for="member of members()">
            <span>{member.name.slice(0, 1)}</span>
            <span>{member.name}</span>
            <span>{member.role}</span>
        </li>
    </ul>

    <div class="nested">
        <b-view src="./team-footer.html"></b-view>
    </div>
</div>

Pass the signals and handlers to the BitsyJS instance that loads the fragments:

import { BitsyJS, signal } from "./bitsy.min.js";

const appName = signal("BitsyJS");
const members = signal([
    { name: "Ada", role: "Engineer" },
    { name: "Grace", role: "Compiler" },
]);

const addMember = () => members.update((list) => [...list, { name: "New member", role: "Guest" }]);
const removeMember = () => members.update((list) => list.slice(0, -1));

const bitsy = new BitsyJS({ data: { appName, members, addMember, removeMember } });

await bitsy.run();

Multiple copies#

Each <b-view> makes its own fetch call, even for the same URL. BitsyJS does not share responses between tags, though the browser or a service worker may serve them from a cache.

Two tags, one src 2 fetch calls
assets/demo/card.html copy 1
assets/demo/card.html copy 2

Each copy keeps its own b-data scope, but both read the global appName, so both conditionals react to the input above.

The demo above is two tags pointing at the same file and nothing else:

<div class="cards">
    <b-view src="../assets/demo/card.html"></b-view>
    <b-view src="../assets/demo/card.html"></b-view>
</div>

Separate copies also mean separate DOM. If the fragment markup carries ids, repeating it duplicates them, so prefer classes inside reusable fragments.

Errors and delivery#

Fragments are fetched with fetch and read as text. A response that is not ok is logged as Response status: 404 and its body is still inlined, so an error page can land inside the document. A request that throws, for example a network failure or a blocked cross-origin request, is logged and produces no content; flattening then throws TypeError: Fragment content must be a string and run() rejects. 

try {
    await bitsy.run();
} catch (error) {
    // a fragment that could not be fetched rejects run()
    console.error("render failed", error);
}

Serve the page over HTTP or HTTPS rather than opening it with file://. For a cross-origin fragment, the server must allow the request via CORS.

Load fragments only from trusted sources. BitsyJS inserts the response as HTML without sanitizing it, and scripts in a fragment can execute when the markup is inserted.
