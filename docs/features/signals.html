Signals

Signals are the reactive layer. A signal holds a value, a computed derives one, and an effect runs a side effect when the signals it reads change. Bindings that read a signal update on their own.

Creating a signal#

A signal holds one value. You read it by calling it and write it with a method, which is why a signal looks like a function and not like a box. 

import { BitsyJS, signal } from "./bitsy.min.js";

const count = signal(0);

count();            // 0, and this read is tracked inside an effect
count.set(5);       // write a value
count.update(n => n + 1); // 6, the callback receives the current value

signal(initial) accepts any value, including arrays, objects and functions. Two helpers identify it: typeof count === "function", and count.__isSignal === true, which is what isSignal checks. Use isSignal(value) rather than the private flag.

Reading, writing and identity#

set(value) compares the new value with Object.is and returns early when they match. Nothing is notified and no binding re-renders, so a write of the same primitive is free. 

const status = signal("idle");

status.set("idle");    // same string, no notification
status.set("running"); // different, every reader is notified

const todos = signal([{ text: "one" }]);

todos.peek().push({ text: "two" });
todos.set(todos.peek());        // same array reference, ignored

todos.set([...todos.peek(), { text: "two" }]); // new array, re-renders

That identity rule is the one trap with arrays and objects. Mutating in place and setting the same reference does nothing, because the library cannot see inside the value. Produce a new value, usually with spread, map or filter.

Three more readers sit next to the call form. peek() returns the value without subscribing, which is what you use when a write needs the current state without adding a dependency. subscribe(callback) registers a plain listener called with the new value and returns { unsubscribe }. Every change is synchronous: by the time set returns, the subscribers and the DOM bindings have run.

Computed values#

computed(fn) derives a value from other signals and exposes it as a read-only signal. It is callable, and it has peek, subscribe and dispose, but no set or update. 

const count = signal(2);
const doubled = computed(() => count() * 2);

doubled();          // 4
count.set(3);
doubled();          // 6
doubled.peek();     // 6, no subscription

doubled.subscribe((value) => console.log("doubled", value));
doubled.dispose();  // stop recomputing, the last value stays readable

A computed is implemented as an internal signal plus an effect, so it recomputes when a signal read during its last run changes. dispose() removes that effect: the value freezes at the last result and no further work happens.

Effects and cleanup#

effect(fn) runs fn immediately, then again whenever a signal that the last run read changes. It returns a disposer. 

const stop = effect(() => {
    console.log("count is", count());
});

count.set(1); // logs again
stop();       // no further runs
count.set(2); // silent

The dependency list is rebuilt on every run: the effect clears what it subscribed to, then tracks whatever the new run reads. So a branch that stops reading a signal also stops waking up for it. 

effect(() => {
    if (enabled()) {
        render(rows()); // rows() is tracked only while enabled() is true
    }
});

Dispose effects you create yourself, or keep the disposer for as long as the effect should live. Bindings and directives create their own effects, and a loop rebuild disposes the set that belonged to the rows it removes.

Which bindings are reactive#

Every directive that reads a signal through an effect updates on its own. The write happens once; the readers do the rest.

Directive Reactive What happens on a write
Text placeholder {count()} Yes, one effect per placeholder Only that placeholder is rewritten
Attribute placeholder class="{state()}" Yes, one effect per attribute The whole attribute value is rebuilt
b-if Yes The element is shown or hidden, never removed
b-js Yes The element's HTML is replaced with the new result
b-for Yes The entire list is cleared and every row rebuilt
b-on:click No The listener is attached once and writes signals itself

Bindings read a signal the same way plain code does: call it. A signal returned from an expression is called for you, so {count} also renders the current value, but {count()} is the clear form and matches {doubled()} for computed values.

Loops rebuild instead of patching. Any change to the array a b-for reads removes all rendered rows, builds new clones, re-binds them and re-attaches their listeners. That is simple and predictable, and it means per-row state belongs in the data, not in the DOM.

Signals come through the constructor#

A b-data attribute is evaluated on its own with new Function. It cannot see module variables, so a signal reference inside it is a hard error rather than an empty scope. 

<!-- run() rejects with "Invalid data string" -->
<div b-data="{ count }">{count()}</div>

<!-- self-contained literals are fine -->
<div b-data="{ step: 1 + 1, label: 'draft' }">{step}</div>

Signals, functions and computed values travel through the constructor's data option, which is the base of every scope. Pass them once and every directive on the page can read them. 

const bitsy = new BitsyJS({
    data: { count, doubled, todos, addTodo, removeTodo },
});

await bitsy.run();

    import { BitsyJS, computed, effect, isSignal, signal } from "./bitsy.min.js";

const count = signal(0);
const doubled = computed(() => count() * 2);

const draft = signal("");
const todos = signal([{ id: 1, text: "Read the signals page" }]);

let nextId = 2;
let logger = null;

const pushLog = (text) => {
    const list = document.querySelector("#signal-effect-log");
    const item = document.createElement("li");

    item.textContent = text;
    list.appendChild(item);

    while (list.children.length > 5) {
        list.removeChild(list.firstElementChild);
    }
};

const watchCount = () => {
    if (!logger) {
        logger = effect(() => pushLog("count is " + count()));
    }
};

const pauseCount = () => {
    if (logger) {
        logger();
        logger = null;
        pushLog("effect disposed, further writes are silent");
    }
};

const addTodo = (event) => {
    event.preventDefault();

    const text = draft().trim();

    if (!text) {
        return;
    }

    todos.update((list) => [...list, { id: nextId++, text }]);
    draft.set("");
};

const removeTodo = (id) => {
    todos.update((list) => list.filter((todo) => todo.id !== id));
};

watchCount();

const bitsy = new BitsyJS({
    data: { count, doubled, draft, todos, isSignal, addTodo, removeTodo, watchCount, pauseCount },
});

await bitsy.run();

    Writing a good update#

    Keep one source of truth and derive the rest. A counter, a computed double and a raw expression all read the same signal, so there is nothing to keep in sync and no observer order to reason about.

    Produce new values instead of mutating, and write once per change: several set calls in one handler render several times, which is correct but wasteful. When a handler needs the current value without creating a dependency, use peek(). When a value must stop updating, keep the disposer returned by effect or call dispose on a computed.
