Data binding

A b-data element creates a scope. Text placeholders and attribute placeholders inside that scope render from it, and re-render when a signal they read changes.

Creating a scope#

A text or attribute placeholder is only bound inside a b-data element. The attribute may be empty, in which case the scope is just the global data from the constructor. 

<div b-data>
    <h1>{appName}</h1>
    <p>Signed in as {user.name}</p>
</div>

The attribute value is a JavaScript object literal, not JSON. Keys can be unquoted, values can be expressions, and nested objects and arrays work. 

<div b-data="{ greeting: 'Hello', score: 10 * 2, user: { name: 'Ada' } }">
    <p>{greeting}, {user.name}. Score: {score}</p>
</div>
The attribute is evaluated on its own. It cannot read variables from your module. Values that live in JavaScript, including signals and functions, belong in the constructor's data option or in the binding expression.

Text placeholders#

In text, {path} is replaced by the value at that path. Dot paths walk objects, and numeric segments index arrays, so {user.social.handle} and {tags.0} both work.

Missing and null values stay as literal placeholders. Everything else updates as you type.

Attribute placeholders#

Placeholders work in attribute values too. A common case is a class or style that depends on state. The whole attribute value is rebuilt whenever one of its placeholders changes. 

<span class="badge {active() ? 'is-on' : 'is-off'}">
    {active() ? 'Active' : 'Paused'}
</span>

<input value="{name()}" b-on:input="name.set($event.target.value)">

For value on inputs, textareas and selects, BitsyJS also writes the DOM property, so the field reflects the signal rather than only its attribute.

Values are HTML#

A rendered value is inserted as HTML, not text. Returning a string with markup creates elements. This is what makes fragments and rich remote data possible, and it is also why values must be trusted.

Missing and null values#

When a path is undefined or null, the placeholder is left exactly as written. That keeps partials readable before their data exists, but it also means a typo stays visible. Check the profile card above: {notInTheData} and {emptyValue} never disappear.

Parsing rules#

The attribute is evaluated as JavaScript, so unquoted keys, trailing commas and expressions are all valid. A value that is a string starting with { or [ is evaluated again and parsed recursively, which is useful when a server hands you a JSON-looking string inside a larger literal. 

<div b-data='{ meta: '{ theme: "dark", compact: true }', flags: '["a", "b"]' }'>
    <p>{meta.theme} / {meta.compact} / {flags.1}</p>
</div>

A string that starts like a collection but cannot be evaluated is left as a string instead of throwing. A value that is a plain string, a number, a boolean or null is stored as written.

Reactive bindings#

Every text and attribute binding runs inside an effect. When a signal read by that binding changes, only that binding updates. A binding that reads no signals renders once and then stays put. 

<div b-data>
    <p>Hello, {name()}</p>
    <p class="{online() ? 'online' : 'offline'}">{online() ? 'Online' : 'Offline'}</p>
</div>

Read more about signal writes in Signals.

What is not bound#

  • <script>, <style> and <template> subtrees are skipped.
  • A nested b-data or b-for element starts its own scope, so the outer bindings do not descend into it.
  • Text outside any b-data element is not bound at all. Directives such as b-js still work there because they evaluate against global data.
  • Attribute names are not interpolated, only attribute values.

Where values come from#

Inside the scope, a path is resolved against the global data merged with the keys on that same b-data element. Nested scopes do not inherit their parent's local keys. The full rules, including loop scopes, are on the Scoping page.
