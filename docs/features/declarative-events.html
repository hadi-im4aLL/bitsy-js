Declarative events

The data-b-event attributes handle the common cases declaratively: swap HTML or text, add, remove or toggle a class, revert after a delay, or fetch a URL.

The event attribute#

data-b-event names the DOM event to listen for, and the matching data-b-event-* attributes describe what should happen when it fires. There is no listener to write and no scope to open: every modifier is a plain string read from the element itself. 

<button type="button" data-b-event="click" data-b-event-text="Saved">
    Save
</button>

The value is passed straight to addEventListener, so any event name works: click, input, change, mouseenter and so on. Modifiers always change the element that carries them, because the handler receives the trigger element, not a target.

Text and HTML#

data-b-event-text replaces textContent and data-b-event-html replaces innerHTML. Both remember the previous value, which is what revert restores later. 

<button type="button" data-b-event="click" data-b-event-text="Copied">Copy</button>

<button type="button" data-b-event="click" data-b-event-html="<strong>Saved</strong>">
    Save
</button>

The HTML modifier inserts markup, not text, so the value in the attribute is the markup you want in the element. Write entities for the angle brackets in your own HTML, as above, and the browser hands the real markup to the handler.

Classes#

Three modifiers change classes: data-b-event-add-class, data-b-event-remove-class and data-b-event-toggle-class. Each one takes a single class name. 

<button type="button" data-b-event="click" data-b-event-add-class="is--loading">Start</button>

<button type="button" data-b-event="click" data-b-event-remove-class="is--loading">Stop</button>

<button type="button" data-b-event="click" data-b-event-toggle-class="is--loading">Toggle</button>

The value goes to classList.add(), classList.remove() or classList.toggle(), which means a value that contains a space throws when the event fires. Two classes need two attributes.

Revert#

data-b-event-revert turns a modifier into a temporary change. The value is read with parseFloat and treated as seconds, so 3, 3s and 1.5 all work. When the delay is over, each modifier undoes itself: text and HTML are put back, an added class is removed, a removed class is added again, and a toggled class is toggled once more. 

<button type="button"
    data-b-event="click"
    data-b-event-text="Saved"
    data-b-event-add-class="is--loading"
    data-b-event-revert="3">
    Save
</button>

One revert value covers every modifier on the element, because each modifier schedules its own undo with the same delay. Remote actions are the exception: they return nothing to undo, so revert has no effect on a fetch.

Several modifiers at once#

Multiple modifiers can sit on the same element. They run in attribute order, which decides the result when two of them touch the same thing. 

<!-- textContent is written last, so the HTML is replaced by plain text -->
<button type="button"
    data-b-event="click"
    data-b-event-html="<strong>Bold</strong>"
    data-b-event-text="Plain">
    Both
</button>

<!-- the class is added and then removed again, so nothing visible happens -->
<button type="button"
    data-b-event="click"
    data-b-event-add-class="is--loading"
    data-b-event-remove-class="is--loading">
    Add then remove
</button>

With revert in play the undos fire after the delay, again in attribute order. Reverse the two class attributes in the second example and the class stays on the element.

Confirm and remote actions#

data-b-event-confirm asks for confirmation with window.confirm before the action runs, and skips the action when the user declines. It is read by the remote handler, so it belongs on a button that fetches. 

<button type="button"
    data-b-event="click"
    data-b-event-remote="../api/users.json"
    data-b-event-target="#user-list"
    data-b-event-indicator="is--loading"
    data-b-event-confirm="Load the user list?">
    Load users
</button>

data-b-event-remote holds the URL, data-b-event-target the selector that receives the response, data-b-event-remote-method and data-b-event-remote-payload the request method and body, and data-b-event-indicator the class that marks the request as running. All of that, and the template machinery behind it, is described on Remote data and templates.

What the attributes cannot do#

  • One event per element. data-b-event holds a single event name, so a button cannot listen for both click and input.
  • Values are literal strings. They are not evaluated and no page data is interpolated into them, so the text you write in the attribute is the text that lands on the page.
  • Modifiers act on the element that carries them. Only the remote action takes a data-b-event-target; text, HTML and class changes always land on the trigger.
  • Listeners are attached once, during run(), to the elements that exist at that moment. Markup added later is not wired.
  • There is no debounce, queue or emit behaviour in the public attributes and no revert for a fetch. A click that fetches sends one request immediately.
  • The data-b-event attributes stay in the DOM. Unlike the b-* directives they are not removed after the run, so the markup keeps describing what it does.
