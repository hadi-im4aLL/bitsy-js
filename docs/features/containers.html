Containers

<b-container> is a layout wrapper that disappears. It groups children while directives run, then is replaced by its own children.

The b-container tag#

<b-container> is a custom element, not an attribute. It groups markup while the library works and then removes itself, so the final DOM holds the children and nothing else. 

<b-container>
    <p>First child</p>
    <p>Second child</p>
</b-container>

After rendering, the page contains the two paragraphs as siblings of whatever surrounded the container. The container has no tag, no attributes and no box of its own. Before run() finishes the browser parses the unknown tag as an inline element, so keep it in a block context to avoid a visible flash of inline layout.

Unwrap timing#

Unwrapping happens late in run(), after fragments, data binding and directives, and before the attributes are flushed and the listeners are attached: 

// fragment.bootstrap()    b-view content inlined
// dataBind.bootstrap()    scopes read, placeholders bound
// directive.bootstrap()   b-for, b-if, b-js
// container.flush()       every b-container replaced by its children
// dataBind.flush()        b-data attributes removed
// eventHandler.listen()   data-b-event and b-on listeners attached

That ordering is why a container can carry a b-data scope. Binding runs while the wrapper still exists, so placeholders inside it resolve from that scope and the rendered children stay where they are. 

<b-container b-data="{ status: 'ready', count: 3 }">
    <p>Status: {status}</p>
    <p>Count: {count}</p>
</b-container>

A data scope is the only reason to put an attribute on an unconditional container, and it only groups data. Styling and identity belong on the children, as the next section shows.

Attributes are discarded#

The unwrap replaces the element itself, so every attribute on it disappears: class, id, style, data-* and anything else. Nothing is copied to the children or to a new wrapper. 

<!-- the class, the style and the id never render -->
<b-container class="card" id="team-panel" style="border: 2px solid red">
    <p>First child</p>
    <p>Second child</p>
</b-container>

<!-- put styling and identity where they survive -->
<div class="card" id="team-panel">
    <b-container>
        <p>First child</p>
        <p>Second child</p>
    </b-container>
</div>

The same rule applies to listeners and ids you planned to target later. If a selector needs to find the group, it has to find a real element.

Nested containers#

Nesting is allowed and every level is removed. All matching tags are collected in one pass, then each one is replaced by its children, which leaves the inner nodes attached to the document and ready for the next replacement. 

<b-container>
    <b-container>
        <p>Child of a nested container</p>
    </b-container>
    <p>Sibling after the nested container</p>
</b-container>

The result is two sibling paragraphs in document order, with no wrapper at either level.

Containers in loops#

A loop clone unwraps its own containers before the cloned row is inserted. That keeps the promise that no container reaches the final DOM, even for rows created long after run(), and nested containers inside a clone are unwrapped too. 

<li b-for="row of rows()">
    <b-container>
        <strong>{row.label}</strong>
        <span>row {_index + 1}</span>
    </b-container>
</li>

Because the loop rebuilds the whole list on every change, adding an item runs the unwrap again for each new clone. The live report below measures that.

One edge case follows from how the clone pass works: it unwraps the clone's descendants, not the clone itself. A <b-container> that carries b-for has its first rows unwrapped by the page-wide flush that runs right after the loops, while rows rendered later keep the container tag. Put b-for on a real element and keep containers inside it.

Conditional containers#

A b-if directly on a <b-container> is the one case where the tag becomes a real element. The condition renames the tag to span and copies its attributes over, so classes and ids survive. The span is then shown with display: inline-block or hidden with display: none, and it is not unwrapped, because it is no longer a container. 

<b-container id="panel" class="pill" b-if="showPanel()">
    Panel children
</b-container>

<!-- after run(), the page holds: -->
<span id="panel" class="pill" style="display: inline-block">
    Panel children
</span>

So the final DOM gains one span with the container's attributes, plus an inline display. If the group must vanish completely, put b-if on a child element or wrap the container in an element that carries the condition.

When to use one#

A container earns its place when markup needs to be grouped for a directive or for readability and the group must not exist in the output: a b-for that has to own several sibling roots, a b-data scope over a few unrelated blocks, or a conditional group whose wrapper cannot stay in the layout.

For everything else, write the element you actually want. A container adds a parsing quirk before run(), drops every attribute you put on it, and hides the fact that the final tree has no grouping element. When layout needs a box, use a real div or section and get the box.
