Event bindings

b-on:event attaches a DOM event listener and runs a statement in the scope of the element. $event is the event, $el is the element, and the current loop item is in scope.

The b-on syntax#

b-on:event="statement" attaches a DOM listener. The text after the colon is the event name, used as written in addEventListener, and the attribute value is JavaScript that runs with the element's scope. 

<button type="button" b-on:click="count.update(n => n + 1)">+1</button>

<input type="text" value="{draft()}" b-on:input="draft.set($event.target.value)">

<form b-on:submit="$event.preventDefault(); save()">
    <button type="submit">Save</button>
</form>

One element can carry several bindings. Each attribute becomes its own listener, so a control can react to a click and to hover without extra wrappers, or to several different events at once. 

<button type="button"
    b-on:click="save()"
    b-on:mouseenter="hovered.set(true)"
    b-on:mouseleave="hovered.set(false)">
    Save
</button>

Every b-on:* attribute is removed during run(). The listener stays attached, the directive attribute does not. A binding with an empty event name or an empty value is removed and skipped, so it never fires.

Statement semantics#

The value is compiled as a function body, not as an expression. Several statements, if blocks and local variables all work, and the result of the last statement is ignored. 

<button type="button" b-on:click="const next = count() + 1; count.set(next); report.set('set ' + next)">
    Increment and report
</button>

The body is not async, so await is a syntax error. Statements are compiled the first time the event fires: a handler that does not compile logs [b-on] syntax error in "..." and that dispatch does nothing. Runtime errors are caught too, as [b-on] runtime error in "...", so a broken handler does not take the page down.

There are no modifiers and no listener options. b-on:click.once listens for an event literally named click.once, which never happens. When you need once, capture or passive, attach that listener yourself with addEventListener.

this inside the statement is the scope object, not the element. Use $el whenever the element itself is needed.

Scope of a listener#

A listener runs with the scope of its element: global data, plus the nearest b-data keys, plus the loop alias and metadata when the element is inside a b-for. That is why a row button can call a function with its own item. 

<li b-for="step of steps()">
    <span>{step.label}</span>
    <button type="button" b-on:click="toggleStep(step.id); report.set('row ' + (_index + 1))">
        Toggle
    </button>
</li>

The scope object is captured when the listener is attached. Values are looked up on each dispatch, so a signal is read live, but a loop row owns the alias it was built with. When the loop rebuilds, the new rows attach new listeners with the new aliases and metadata, and the old listeners are removed with the old nodes.

The event object#

$event is the DOM event and $el is the element that carries the attribute. Both are injected on dispatch and shadow any data key with the same name. 

<div b-on:click="report.set('target ' + $event.target.tagName + ', element ' + $el.tagName)">
    <span>Click the label</span>
</div>

event.target is the deepest element that was clicked, so it can be a child, while $el is always the element with the binding. For buttons that contain markup, that difference decides which element you read from.

Nothing is prevented for you. A form submits, a link navigates and a keypress does whatever the browser does, unless the statement says otherwise. Cancel a submit with $event.preventDefault(), stop a bubbling click with $event.stopPropagation(), and read typed text from $event.target.value. 

<form b-on:submit="$event.preventDefault(); submitForm($event)">
    <input type="text" b-on:input="draft.set($event.target.value)">
    <button type="submit">Send</button>
</form>

Any DOM event#

The name is passed straight to addEventListener, so every DOM event works: click, dblclick, input, change, focus, blur, keydown, keyup, mouseenter, mouseleave, submit, copy, dragstart and the rest. A custom event dispatched on the element works the same way, for example b-on:team-updated.

Choose the event by what you need to observe. input fires on every keystroke, change fires when a field loses focus with a new value, and keydown gives you the key before the value changes.

Listener lifecycle#

Listeners are attached in run() after fragments, bindings, directives and the container flush, which has three consequences worth knowing.

  • An event dispatched before run() resolves has no handler. The markup shows, but nothing is wired yet.
  • A b-on on a <b-container> is lost. The wrapper is removed before, or immediately after, the scan, so the element that carried the attribute never survives. Put behavior on a child.
  • Elements added to the DOM after run(), by a remote response, by data-b-event-html or by your own code, are never scanned. Their b-on attributes stay in the DOM as inert text.

Loop rows are the exception, because the loop owns them: every rebuild attaches listeners for the new clones and disposes the old ones. For markup you create yourself, use addEventListener directly, or attach one listener to a stable parent and let events bubble to it.

    Rules of thumb#

    Keep statements to one call into page code. A binding that reads like b-on:click="removeTodo(todo.id)" is greppable, testable and short, while a paragraph of logic in an HTML attribute is none of those. Use the statement form for the small cases, such as incrementing a counter or cancelling a submit, and move the rest into the data object.

    Put bindings on the element that actually receives the event. Because $el is fixed to that element and there is no automatic delegation, a binding on a wrapper has to read $event.target and decide for itself. When a group of controls shares behavior, one listener on the parent with a closest check is usually simpler than one binding per child.
