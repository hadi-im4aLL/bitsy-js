Scoping

Global data is the base for every scope. A b-data scope adds its own keys, and a loop adds its item alias and metadata. Scopes are flat, not inherited.

Global data is the base#

The data object you pass to the constructor is the base for every scope on the page. A b-data element with no keys, an empty b-data attribute, and a directive outside any scope all start from that same data. 

<div b-data>
    <p>{appName} rendered this scope.</p>
</div>

<p>{appName}</p>
<!-- left as written: text placeholders only bind inside a b-data element -->
const bitsy = new BitsyJS({
    data: { appName: "BitsyJS docs", theme: "global-dark" },
});

Directives such as b-if, b-js, b-for and b-on read global data anywhere on the page. Text and attribute placeholders are the exception: they need an enclosing b-data element, as described in Data binding.

One shallow merge per scope#

Each b-data element builds its scope with a single shallow merge: global data first, then the keys from its own attribute. Its own keys win, keys it does not define still come from global data, and nothing is copied deeper than the first level. 

<div b-data="{ theme: 'local-light', badge: 'Beta' }">
    <p>theme: {theme} from the local scope</p>
    <p>appName: {appName} from global data</p>
    <p>badge: {badge} exists only here</p>
</div>

The attribute is a standalone JavaScript object literal, not JSON. Unquoted keys, nested objects, arrays and expressions all work, and the object is evaluated before the merge happens. 

<div b-data="{ count: 0, label: 'clicks', limits: { min: 0, max: 10 } }">
    <p>{label}: {count} of {limits.max}</p>
</div>

Scopes are flat, not nested#

Nested b-data elements do not chain. A child scope is built from global data plus its own keys only, so it never inherits, merges with, or looks through the local keys of its parent. 

<div b-data="{ outer: 'outer value' }">
    <p>{outer} is bound here.</p>

    <div b-data="{ inner: 'inner value' }">
        <p>{inner} is bound, {outer} is not, {appName} comes from global data.</p>
    </div>
</div>

Because outer is not part of the nested scope, {outer} is left exactly as written. Missing values are never cleared, so the mistake is visible instead of silent.

The fix is structural: keep b-data elements as siblings, repeat the keys each scope needs, or move the shared value into global data. Do not rely on a parent scope to supply child keys.

Which scope a directive reads#

Bindings and directives resolve against one scope at a time. Nothing reads a sibling scope, and nothing walks upward past the nearest match.

Directives and the scope they read
Directive Scope it reads
placeholders Text and attribute placeholders read global data plus the keys of the enclosing b-data element.
b-if, b-js, b-on Global data, the nearest b-data element, and the row scope inside a loop.
b-for Global data plus the nearest b-data element; every row then gets its own scope.
b-view No scope of its own. The fragment is inlined before any scope is created, then binds with the surrounding scope.
b-container No scope of its own. The wrapper disappears and its children bind with the scope around them.

Nearest means the element itself when it carries b-data, otherwise the closest ancestor that does. A directive on the same element as a b-data scope already sees that scope's keys.

Loop scope#

A row scope is built from the scope the loop element itself sees, plus the item alias and three metadata keys. Global keys and the nearest b-data keys therefore stay visible inside the loop, which is what makes {appName} and {store} work in the demo above. 

<div b-data="{ store: 'Northwind' }">
    <ul>
        <li b-for="item of items">
            <span>{_index}. {item.name}</span>
            <span b-if="_isFirst">first row</span>
            <span>store {store} on {appName}</span>
        </li>
    </ul>
</div>

The loop captures its list scope once, when it binds, and every row is built from that snapshot. Values added to global data afterwards do not reach a row, and a row never sees another row's alias. Use _index when a row needs to read the source array. See Loops for the full descriptor rules and metadata.

Objects are replaced, not merged#

The merge is one level deep, so a local key replaces the global value as a whole object. Keys of the global object do not survive underneath it. 

<!-- global data: user: { name: 'Global user', role: 'guest' } -->
<div b-data="{ user: { name: 'Local user' } }">
    <p>name: {user.name}</p>
    <p>role: {user.role}</p>
</div>

The local user object wins, so {user.name} renders the local name and {user.role} stays unresolved because the replacement object has no role. Pass the complete object, or pass a signal that returns the complete object.

What b-data cannot see#

A b-data attribute is compiled and called on its own, outside your module. It cannot read module variables, imported values, or functions you defined, and it cannot call a signal unless you put that signal in the constructor data. 

<!-- userName lives in your module, so this attribute cannot read it -->
<div b-data="{ name: userName }"></div>

Referencing a name that does not exist in that context does not fall back to something empty: scope setup fails and run() rejects. Pass the value through the constructor instead.

Browser globals such as Math and Date are reachable because the attribute is ordinary code, which also means the attribute is code you must trust. Everything from your module has to arrive through the constructor. 

const bitsy = new BitsyJS({ data: { userName, greet } });
<div b-data="{ greeting: 'Hello' }">
    <p>{greeting}, {userName}!</p>
    <p b-js="greet(userName)"></p>
</div>

The same rule applies to directive expressions: they are evaluated with the scope you gave them. Read Security before binding anything a user can influence.
