Loops

b-for repeats the element it is on, once per item, and gives each copy an item alias plus _index, _isFirst and _isLast.

Syntax and the alias rule#

b-for takes a descriptor with two parts: a single-word alias, the keyword of, and the list expression. The attribute is read as <alias> of <list expression>, and the whitespace around of is required. 

<ul>
    <li b-for="member of members()">{member.name}</li>
</ul>

The alias is an ordinary variable name built from letters, digits and underscores. It cannot be a destructuring pattern and it cannot be omitted, so b-for="member in members()" and b-for="members()" do not match the descriptor. A descriptor that does not match is ignored: the element stays in the document, renders once as written, and keeps its unused attribute.

The list expression is evaluated in the scope the element sits in, so a path such as rows, a nested path such as report.rows, and a signal call such as members() are all valid. Read more about scope in Scoping.

Arrays only, and empty means nothing#

The resolved value must be an array. A signal that returns an array is called for you. Anything else, including a string, an object, a number, null or a missing path, renders no rows at all and raises no error. An empty array is the same case: zero rows, nothing to show. 

<ul>
    <li b-for="tag of tags">{tag}</li>
</ul>

<p b-if="tags.length === 0">No tags yet.</p>

b-for has no empty branch of its own. Put a b-if next to the list and branch on the array length, or use roster().length when the list comes from a signal, as in the demo below.

Loop metadata#

Every row gets three extra keys on top of the item alias: _index is the zero-based position, _isFirst is true on the first row, and _isLast is true on the last row. They are ordinary values, so placeholders, b-if, b-js and b-on can all read them.

Metadata markers _index, _isFirst, _isLast
  • {_index}. {step.label} first last even index

_isFirst and _isLast are both true when the array holds a single item. The metadata is computed when the row is built, so it follows the current array rather than the original one.

Nested object and array paths#

Row values are reachable through dot paths, and a numeric segment indexes an array. {order.customer.name} walks objects, while {order.lines.0.sku} reads the first line. Numeric segments are also rewritten to bracket notation before the expression runs, so both spellings resolve.

Paths inside a row nested fields
  • {order.id} | {order.customer.name} first line {order.lines.0.sku} | {order.lines.length} lines 
<li b-for="order of orders">
    <span>{order.customer.name}</span>
    <span>{order.lines.0.sku} / {order.lines.length} lines</span>
</li>

Every value in a placeholder is an expression, so small derivations such as {order.lines.length - 1} or {order.total.toFixed(2)} work without adding a helper to the row scope.

A live list with add and remove#

When the list expression reads a signal, the whole loop is reactive. Adding or removing an entry rebuilds the rows from the current array, so metadata such as _isFirst and _isLast stays correct. The row button receives the item alias, which is why it can pass an id back to a function from the constructor data.

Roster
  • {member.name} idx {_index} | first {_isFirst} | last {_isLast} | {member.role}

The roster is empty, so the loop renders no rows at all. The empty-state paragraph is a separate b-if. 

<ul>
    <li b-for="member of roster()">
        <span>{member.name}</span>
        <button b-on:click="removeMember(member.id)">Remove</button>
    </li>
</ul>

<p b-if="roster().length === 0">The roster is empty.</p>

Remove every member to see the empty state. The row count in the badge is a b-js expression, so it also updates with the array.

Conditions and events inside a row#

A row is its own scope, so b-if and b-on on or inside the row read the item alias and the metadata. Conditions are re-evaluated when a signal they read changes, and each row gets its own listener with the same scope. 

<li b-for="job of jobs">
    <span>{job.name}</span>
    <span b-if="_isFirst">starts the queue</span>
    <span b-if="job.enabled">enabled</span>
    <span b-if="!job.enabled">disabled</span>
    <button b-on:click="run(job.id, $event)">Run</button>
</li>

$event and $el work inside a row exactly as they do outside one. A condition placed on the element that carries b-for is evaluated per row as well, because every clone keeps that attribute until it is processed. The row is hidden rather than removed, so the document keeps one element per filtered item; filter the array before it reaches the loop when that matters.

Fragments inside a loop#

Fragments are inlined before directives run, so a b-view inside a b-for element becomes part of the loop template. The inlined markup binds with the row scope, which means the fragment can use the item alias even though it was written in a separate file.

One fragment per row b-view and b-for 
<div b-for="member of crew">
    <b-view src="./member-row.html"></b-view>
</div>

<!-- member-row.html -->
<div class="row">
    <span>{member.name}</span>
    <span>{member.role}</span>
</div>

The alias in the loop descriptor and the placeholders in the fragment have to agree. Here the loop uses member, which is what the fragment expects. See Fragments for nested paths and fragment loading rules.

Containers inside a loop#

A <b-container> inside a row keeps the row markup grouped while directives run, then disappears. The rows in the roster demo use one, so the spans and the metadata line end up as direct children of the list item. 

<li b-for="member of roster()">
    <b-container>
        <span>{member.name}</span>
        <b>{_index} / {member.role}</b>
    </b-container>
    <button b-on:click="removeMember(member.id)">Remove</button>
</li>

The container is unwrapped per row, both when the row is first built and when the loop rebuilds it. Only the container itself is discarded; the elements inside keep their bindings and listeners. Read Containers for the standalone behaviour.

Rows are recreated, not patched#

b-for replaces itself with an empty comment anchor and inserts cloned rows after it. When a signal read by the list expression changes, the previous rows are removed and new clones are built from the template, which is why no diffing is involved.

The consequence is that row-local DOM state does not survive a rebuild. Text typed into an input inside a row, an open disclosure, focus, scroll position or a third-party widget attached to the row is lost when the array changes. Keep such state in signals or outside the loop. 

const roster = signal([{ id: 1, name: "Ada", role: "admin" }]);

function addMember() {
    roster.set([...roster.peek(), { id: 2, name: "Grace", role: "editor" }]);
}

function removeMember(id) {
    roster.set(roster.peek().filter((member) => member.id !== id));
}

Each rebuild also disposes the effects and listeners of the old rows before attaching new ones, so a long-lived page does not accumulate handlers. Keep row markup cheap and move expensive work into a signal or a computed.
