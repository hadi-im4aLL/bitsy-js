Comparison

Plenty of libraries work without a build step. The better question is: where do you want to edit the UI tomorrow? In an HTML file, in a server template, or in a JavaScript component?

Choose by workflow#

  • Keep plain HTML files and add a few features: Start with BitsyJS if you want shared partials, data bindings, and simple forms in one library. Use Alpine.js if local interactive state is most of what you need.
  • Only need to include another HTML file? Use <include-fragment> or <h-include>. Reach for BitsyJS when those partials also need bindings, loops, or shared data.
  • Let the server render updates: Start with htmx for targeted HTML replacements, Unpoly for navigation and form flows, or Datastar when you also want signals and streamed server updates.
  • Write the UI in JavaScript: Pick a component or reactive rendering library. Lit is a good fit for custom elements; Mithril.js makes more sense when the app also needs routing and request utilities.
  • Only need one small behavior? Native HTML and a little JavaScript may be enough. If your only missing piece is client-side routing, a router like Page.js is a more direct fit.

Compare libraries#

These are starting points, not feature checklists. Several tools can solve the same problem with custom code or extensions.

Libraries and tools by primary use case
Library Reach for it when
BitsyJS You want existing HTML to load partials, bind data, render JSON with local templates, and handle simple forms. Plain data renders once; signals opt specific bindings into updates.
@github/include-fragment-element You want a custom element that fetches an HTML fragment and replaces itself with the result. It supports fallback content and optional lazy loading. If you only need includes, you don't need a full data-binding library.
h-include You want to fetch HTML into a custom element without replacing the wrapper. It also supports conditional includes and an alternate URL if the request fails.
Web Fragments You want independently deployed micro-frontends that can coexist in one page, for example during a gradual migration. That's a different job from including a shared header.html in a static site.
Alpine.js You want reactive state, loops, conditions, and events directly in HTML. This is the closest fit if your main job is wiring up interactive widgets rather than assembling pages from files.
petite-vue You are enhancing existing markup and already like Vue-style bindings and reactivity. BitsyJS instead bundles file-based partials and basic request and form helpers.
htmx Your endpoints return HTML and you want requests and swaps declared in the markup. BitsyJS can also render JSON into a template in the current page.
Datastar You want browser-side signals plus server-driven updates, including streamed HTML or signal patches. BitsyJS does not require a server patch protocol.
Unpoly You want partial page updates as users navigate and submit forms on a server-rendered site. BitsyJS enhances the current page and leaves ordinary navigation alone.
Stimulus Your HTML is already rendered and you want to organize its behavior in JavaScript controllers. BitsyJS also provides directives for rendering, including loops and partials.
_hyperscript You want to write event-driven behavior in a small language embedded in HTML. BitsyJS uses JavaScript expressions and covers data rendering as well as events.
Preact + HTM You want Preact components without compiling JSX. HTM lets you write component markup in JavaScript template literals rather than adding directives to an existing HTML file.
VanJS You want reactive state and real DOM elements created with JavaScript functions, without a virtual DOM. BitsyJS starts with DOM elements already on the page.
Lit You want to ship reusable custom elements with reactive properties and templates. BitsyJS is for enhancing pages rather than defining a component library.
Mithril.js You want client-side components, routing, and HTTP utilities together. Mithril manages the app's rendered views with a virtual DOM; BitsyJS does not own the whole app.
ArrowJS You want reactive templates written in JavaScript without a virtual DOM. With BitsyJS, bindings and loops live in the HTML you already edit.
Page.js You only need to map browser URLs to handlers. It is a router, not a renderer, so you can use it alongside a view library rather than instead of one.

When BitsyJS fits#

Say you're making a docs site or a landing page. You want to include a shared header, render a list from links.json, and validate a contact form. BitsyJS does those together. Serve the HTML and JSON over HTTP from a static host; you only need a form endpoint if you're actually accepting submissions.

Pick something else if the project mainly needs client-side routing, reusable components, or substantial shared client state. If essential content has to work without JavaScript, put it in the initial HTML or pre-render it. If your content security policy blocks dynamic code evaluation, check the expression limitations before choosing BitsyJS.
