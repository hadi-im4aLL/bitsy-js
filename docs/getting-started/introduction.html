Introduction

BitsyJS is a tiny view layer for HTML that is already on the page. It reads attributes, binds data, repeats blocks, shows and hides elements, loads fragments, wires events and validates forms, then removes the attributes it used.

What it is#

BitsyJS enhances existing HTML after the page loads. It reads directives from the DOM and fills in data, repeats blocks, shows or hides elements, loads fragments, wires events, fetches remote data and validates forms. There is no virtual DOM, component compiler, runtime dependency or build step for consumers.

It is built for HTML produced by server-side apps, static site generators or hand-written pages. The markup that reaches the browser is the markup the user reads, whether or not the script runs.

  • Keep the HTML you already have. There is no separate template language.
  • Avoid a build step. Import from npm or a CDN and call run().
  • Stay declarative. Directives are ordinary attributes or custom tags.
  • Render once by default. Use signals where the page needs to respond to changes.
  • Reuse server partials. Inline them with b-view.
  • Improve pages progressively. If JavaScript fails, the original markup remains.
Not a framework replacement. BitsyJS is not a replacement for React, Vue or Svelte in highly interactive applications. It is for pages that are mostly rendered already.

When to use it#

The library earns its place when the server already knows what the page should say. It works best on pages with a small number of interactive regions and a lot of static content.

Good fit

  • Server-rendered pages and admin screens
  • Static sites that need a little behaviour
  • Progressive enhancement on existing markup
  • Pages that render once and then settle

Poor fit

  • Highly interactive applications
  • Teams that want a component compiler
  • Markup that only exists on the client
  • Apps that need a large ecosystem of plugins

The mental model#

Think of one pass over the page. BitsyJS loads fragments, resolves scopes, renders bindings, removes the directive attributes it consumed, then attaches event and form handlers. After that pass the document is ordinary HTML with ordinary listeners. Reactivity is opt-in: only bindings that read a signal keep updating.

After run() resolves, the values are in place and the directive attributes are gone. Inspect the document and you will find plain HTML, not a component tree.

How a render runs#

run() is asynchronous and always works in the same order. Each step finishes before the next one starts.

  1. Fragments load. b-view fetches partials, and nested paths resolve relative to the parent.
  2. Scopes attach. Global data is the base, and each b-data adds its own keys.
  3. Bindings apply. Placeholders, b-for, b-if and b-js render.
  4. Containers unwrap. <b-container> is replaced by its children.
  5. Directives are removed. The attributes that ran no longer exist on the page.
  6. Events and forms attach. b-on listeners and validation forms are wired.
  7. bitsy.rendered fires. Callbacks registered with ready() or on("rendered") run.

Listeners registered after the first render wait for the next one. See Lifecycle for the details.

Directives at a glance#

Five directives are attributes and two are custom tags. Each one is removed or unwrapped once it has done its work.

Core directives and their syntax
Directive Syntax Purpose
b-data <div b-data> Creates a local scope for placeholders and nested directives.
b-for <li b-for="item of items"> Repeats the element for each item and exposes loop metadata.
b-if <p b-if="isReady"> Shows or hides an element with display: none.
b-js <span b-js="total()"> Evaluates an expression and writes the result as HTML.
b-on <button b-on:click="save()"> Runs JavaScript in the current scope on any DOM event.
b-view <b-view src="./card.html"> Fetches an HTML fragment and inlines it at the element.
b-container <b-container> Groups markup and removes its own wrapper after rendering.
data-b-* data-b-event, data-b-validate Declarative events, remote templates and form validation.

Data and scopes#

Global data from the constructor is the base for every scope. A b-data element adds its own keys on top. Scopes are flat: a nested b-data does not inherit the local keys of its parent. Directives and bindings always read the nearest scope plus global data.

  • b-data shallow-merges its keys over global data.
  • b-for adds the item alias, _index, _isFirst and _isLast.
  • b-if, b-js and b-on read the nearest scope; b-if and loops also see loop metadata.
  • Local objects replace global objects as a whole value. There is no deep merge.

Read the full rules in Scoping.

Signals#

Use signal(initialValue) for state that changes after run(), and computed(() => ...) for values derived from signals. Pass both in the constructor's data and call them as functions in bindings. 

import { BitsyJS, computed, signal } from "./bitsy.min.js";

const count = signal(0);
const doubled = computed(() => count() * 2);

const bitsy = new BitsyJS({ data: { count, doubled } });
await bitsy.run();

Events and forms#

b-on:event runs JavaScript in the current scope. $event is the DOM event, $el is the element that owns the handler, and the current loop item is in scope when there is one. Declarative data-b-event attributes cover the common click effects, and forms can validate and submit with fetch using the same attribute pattern. 

<form
    action="/signup"
    method="post"
    data-b-validate-form="true"
    data-b-form-ajax="true"
    data-b-form-ajax-target="#result"
>
    <input name="email" data-b-validate="required|email" />
    <small data-b-validate-message="email"></small>
    <button type="submit">Sign up</button>
</form>

See Event bindings, Forms and Validation.

Security#

Only evaluate what you trust. BitsyJS evaluates directive expressions with new Function, and expressions can reach browser globals. HTML values, fragments and remote responses are inserted as markup. Never pass untrusted user input into them.

Read the full trust model in Security.
