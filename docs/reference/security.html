Security

BitsyJS evaluates JavaScript and can insert HTML. Use only trusted templates, and keep untrusted input out of expressions and HTML insertion paths.

The trust model#

BitsyJS does not sanitize HTML or enforce an origin or URL allowlist. Your app must decide which templates, URLs and values to trust.

Keep code and data separate. Author directive expressions and b-view fragments yourself. Keep untrusted values out of HTML insertion paths unless they have been sanitized for that use.
  • Markup is authored. Attributes such as b-if, b-on:click and data-b-event-html are part of the template, written by your server or your source files.
  • Data stays untrusted. Passing user input through the constructor or a signal does not make it safe to render as HTML.
  • Request URLs are configuration. Keep fragment and endpoint URLs under your control. Validate any dynamic URL before giving it to BitsyJS.
  • Readiness is not permission. window.__bitsyRendered and the bitsy:rendered event only describe lifecycle state.

Expression evaluation#

Directive expressions are compiled with new Function at run time. The evaluation form wraps the expression in a with block over a scope proxy: 

new Function("__s__", `with (__s__) { return (${expression}); }`);

b-on uses the statement form, which drops the return and executes the text as a function body. Compiled functions are cached per expression string, but they are still compiled at run time from the attribute text that is on the page.

The scope proxy looks up names in the merged data first, then in globalThis. It is not a sandbox. If a name is missing from both, the lookup returns undefined.

How identifiers resolve inside a directive expression
Expression Resolves to
title The title key in the current scope.
fetch globalThis.fetch, the browser function.
document The real document. Expressions can read and mutate the page.
localStorage The real storage object, including whatever your app stored there.
location The real location. Assigning to it navigates.

Expressions run with the page's privileges. Never build an expression from user input or let users supply expression attributes.

BitsyJS evaluates b-data separately with new Function, without the scope proxy. Treat these attributes as JavaScript, not JSON. Pass module variables, including signals, through the constructor's data option.

Where HTML is inserted#

Rendered values do not always become text. The library has several insertion points, and most of them parse HTML.

How BitsyJS inserts content into the DOM
Point Sink What that means
Text placeholder inside b-data Parsed nodes when the value looks like markup, otherwise a text node A value containing a tag is inserted as elements, not shown as text.
Attribute placeholder inside b-data setAttribute No HTML parsing, but the value can be a URL, a style or an inline handler if the attribute is one.
b-js element.innerHTML The result is parsed as markup, including event handler attributes.
b-view fragment Range.createContextualFragment The fetched document is inlined and then processed, so a fragment can carry directives and expressions.
Remote response without a template element.innerHTML Strings are inserted directly. Objects are pretty-printed with JSON.stringify and then assigned to innerHTML, so < inside a string value is still parsed as markup.
Template rendering template.innerHTML plus a cloned fragment BitsyJS substitutes response values into HTML and processes directives if the template contains b-for or b-if.
data-b-event-html element.innerHTML Markup from the attribute is inserted on the event.
data-b-event-text element.textContent Displays the attribute value as text, without parsing HTML.
AJAX form response Same renderer as remote responses The response replaces target content by default. Template rendering can also append.

Do not rely on browser script handling to make inserted HTML safe. Treat fetched fragments as active page content. Even where script elements do not execute, markup can still contain event handlers or load external resources.

Remote data and fragments#

b-view fetches its src, and a declarative event fetches the URL in data-b-event-remote. Both use browser fetch and are subject to its security rules.

  • Limit request targets. Allowlist schemes and origins for any URL your app puts in a request attribute.
  • Responses can become markup. JSON is not a safety boundary: when a response is rendered, user content can reach an HTML insertion point.
  • Serve fragments as trusted templates. BitsyJS inserts them before processing directives. Use endpoints you control, and do not mix user HTML into fragment responses.
  • Request options are attributes. data-b-event-remote-method sets the method and data-b-event-remote-payload sets the JSON body for non-GET methods. JSON payloads are sent with Content-Type: application/json by default. Set data-b-event-remote-content to another value to skip that header.
  • CORS applies. A cross-origin endpoint must allow the requesting origin for BitsyJS to read the response. The default fetch credentials mode sends cookies only on same-origin requests.
  • Confirmation is not authorization. data-b-event-confirm and data-b-form-confirm call window.confirm, which the user can bypass and the server cannot see.

Content security policy#

BitsyJS uses new Function to compile expressions. If your content security policy (CSP) blocks dynamic evaluation, hashes and nonces on the scripts that load BitsyJS do not authorize it.

When CSP blocks new Function:

  • b-if, b-js and b-on log a syntax error when compilation is attempted. Placeholders and b-for fall back silently.
  • A b-data literal fails to parse, which throws a SyntaxError and rejects run().
  • There is no expression-free mode: placeholders, b-if, b-js, b-on and b-for all compile through the same evaluator.

Trusted Types enforcement also affects HTML insertion. With require-trusted-types-for 'script', sinks such as innerHTML and Range.createContextualFragment reject plain strings unless a default policy handles them. BitsyJS does not provide a policy.

Adding 'unsafe-eval' weakens CSP for the whole page, not just BitsyJS. If your policy must block dynamic evaluation, choose a renderer that does not compile expressions at runtime.

Sanitization guidance#

Choose a text-only output path for plain text. If you need HTML, sanitize it for the insertion point before BitsyJS renders it.

  1. Keep untrusted values out of directive attributes and out of any string that becomes an expression.
  2. Use textContent for untrusted plain text. If you must pass plain text through an HTML text context such as the b-js demo below, HTML-escape it first. Text escaping is not URL or attribute validation.
  3. If you must render user HTML, sanitize it with a dedicated library such as DOMPurify. Keep the result out of templates and fragments that BitsyJS processes as directives.
  4. For declarative text updates, prefer data-b-event-text over data-b-event-html.
  5. Allowlist URL schemes for anything that lands in href, src or a remote attribute. Reject javascript: and unexpected origins.
  6. Do not treat a client-side check as a boundary. See the next section.

Validation and secrets#

BitsyJS checks data-b-validate rules on submit and shows feedback with classes and messages. Browser checks can be bypassed. Validate every request and enforce authorization on the server.

  • validatorConfig changes text and class names, not enforcement.
  • BitsyJS reads custom text from data-b-validate-error-message and writes it with textContent to the matching data-b-validate-message element.
  • Apply the same server-side checks to AJAX submissions as to regular form submissions.

Keep secrets out of browser data and static output:

  • Constructor data is available in the browser and can end up in the DOM, a pre-rendered HTML file or a console log.
  • Attributes are public too. An API key in data-b-event-remote or in a payload attribute is readable by anyone who opens developer tools.
  • Browser requests carry cookies and headers, and their responses are visible to the user. Secrets belong on the server, behind an endpoint that does the privileged work.
  • Prerendered output is static HTML. Whatever was rendered at capture time is in the file, so render only what may be published.
