Security

BitsyJS is not a sanitizer. Directive expressions are JavaScript, and rendered values, fragments and remote responses are inserted as markup. Treat every one of them as trusted code.

The trust model#

BitsyJS is a renderer, not a sanitizer. It has no origin checks, no URL allowlist, no HTML filtering and no distinction between a value you wrote and a value a user supplied. It takes strings and does what the markup says: evaluates them, fetches them or inserts them into the DOM.

Every one of these is trusted code. Directive expressions, values rendered into the page, fragments fetched by b-view, endpoints named by data-b-event-remote and bodies returned by them. If an attacker can influence any of them, they can influence the page.

The practical rule is narrow and easy to check: the data you render must be data you produced or vetted.

  • Markup is authored. Attributes such as b-if, b-on:click and data-b-event-html are part of the template, written by your server or your source files.
  • Data is content. Values from the constructor and from signals are inserted into that markup and must be treated as untrusted until proven otherwise.
  • Fragments and endpoints are configuration. Every URL the library fetches comes from an attribute, so injecting an attribute is as good as injecting a request.
  • Readiness is not permission. window.__bitsyRendered and the bitsy:rendered event only describe lifecycle state.

Expression evaluation#

Directive expressions are compiled with new Function at run time. The evaluation form wraps the expression in a with block over a scope proxy: 

new Function("__s__", `with (__s__) { return (${expression}); }`);

b-on uses the statement form, which drops the return and executes the text as a function body. Compiled functions are cached per expression string, but they are still compiled at run time from the attribute text that is on the page.

The scope is a Proxy that reports every identifier as present and resolves it in two steps: the merged data object first, then globalThis. Unknown names therefore do not throw a ReferenceError; they fall through to the browser global object.

How identifiers resolve inside a directive expression
Expression Resolves to
title The title key in the current scope.
fetch globalThis.fetch, the browser function.
document The real document. Expressions can read and mutate the page.
localStorage The real storage object, including whatever your app stored there.
location The real location. Assigning to it navigates.

Two consequences follow. First, expressions are code: never build one by concatenating data into an attribute, and never let user input reach an attribute that holds an expression. Second, a page that relies on expressions can reach anything the page itself can reach, so the question is never whether BitsyJS is safe but whether the strings you give it are.

b-data literals are evaluated separately with new Function("return (" + source + ")")(), without the scope proxy. They see literals and browser globals but not your signals, which is why module values have to be passed through the constructor's data option.

Where HTML is inserted#

Rendered values do not always become text. The library has several insertion points, and most of them parse HTML.

Every place BitsyJS inserts content into the DOM, with the sink it uses
Point Sink What that means
Text placeholder inside b-data Parsed nodes when the value looks like markup, otherwise a text node A value containing a tag is inserted as elements, not shown as text.
Attribute placeholder inside b-data setAttribute No HTML parsing, but the value can be a URL, a style or an inline handler if the attribute is one.
b-js element.innerHTML The result is parsed as markup, including event handler attributes.
b-view fragment Range.createContextualFragment The fetched document is inlined and then processed, so a fragment can carry directives and expressions.
Remote response without a template element.innerHTML Strings are inserted directly. Objects are pretty-printed with JSON.stringify and then assigned to innerHTML, so < inside a string value is still parsed as markup.
Template rendering template.innerHTML plus a cloned fragment The template body is rewritten with the response values and its directives are run against them.
data-b-event-html element.innerHTML Markup from the attribute is inserted on the event.
data-b-event-text element.textContent Text only. This is the safe option for values you do not control.
AJAX form response Same renderer as remote responses The response replaces or appends to the target using the same rules.

Inline <script> elements inserted this way do not execute, but inline event handler attributes do, and so does anything that loads a resource when it is added to the document. Treat every sink in the table as equivalent to assigning innerHTML.

Remote data and fragments#

b-view fetches its src, and a declarative event fetches the URL in data-b-event-remote. Both are plain fetch calls made from the browser with the page's origin and no special headers.

  • URLs come from attributes. If an attacker can inject or edit an attribute, they choose the request target and the markup that comes back.
  • Responses become markup. JSON, text and HTML responses all end up in the same render path, so an endpoint that echoes user content is a rendering path for that content.
  • Fragments are executable configuration. A fetched fragment is inlined before directives run, so it can contain b-if, b-on and expressions. Serve fragments from your own origin.
  • Request options are attributes. data-b-event-remote-method sets the method and data-b-event-remote-payload sets the JSON body for non-GET methods. Note that no Content-Type header is sent: the library passes a header property where fetch expects headers, so the header object is ignored.
  • CORS applies. A cross-origin endpoint has to allow the requesting origin. The library does not set a credentials mode, so fetch defaults apply and cross-origin cookies are not sent.
  • Confirmation is not authorization. data-b-event-confirm and data-b-form-confirm call window.confirm, which the user can bypass and the server cannot see.

Content security policy#

Because expressions are compiled with new Function, a page that uses them needs a policy that allows evaluation, for example script-src 'self' 'unsafe-eval'. Hashes and nonces do not help, because the code does not exist until run time.

Without that exception new Function throws, and the library cannot do its work:

  • Expression directives log [tag] syntax error in "..." and fall back: placeholders keep the raw {path} text, b-if hides its element and b-for renders no rows.
  • A b-data literal fails to parse, which throws a SyntaxError and rejects run().
  • There is no expression-free mode: placeholders, b-if, b-js, b-on and b-for all compile through the same evaluator.

Trusted Types is a second constraint. Assigning to innerHTML and calling Range.createContextualFragment are both sinks, so a policy with require-trusted-types-for 'script' makes those assignments throw unless the page registers a trusted type policy. The library does not ship one.

Adding 'unsafe-eval' to a policy is a real weakening of that policy. Add it only when every expression on the page is authored by you and every value they can read is trusted.

Sanitization guidance#

The library gives you no sanitizer, so the escaping and filtering is yours. Do it where untrusted data enters the page, not inside directives, and prefer the narrowest sink that does the job.

  1. Keep untrusted values out of directive attributes and out of any string that becomes an expression.
  2. Escape text you want displayed literally: replace &, < and > before rendering.
  3. If you must render user HTML, sanitize it with a dedicated library such as DOMPurify and render the sanitized result. Sanitizing at the render call means every new insertion point has to remember to do it.
  4. Prefer data-b-event-text over data-b-event-html for any value you did not author.
  5. Allowlist URL schemes for anything that lands in href, src or a remote attribute. Reject javascript: and unexpected origins.
  6. Do not treat a client-side check as a boundary. See the next section.

Validation and secrets#

Validation in BitsyJS is form UX. Rules are read from data-b-validate, checked in the browser on submit, and answered with classes and messages. A user can edit the attributes, skip the handler, replay the request with curl or disable JavaScript entirely. Every rule has to exist on the server as well.

  • validatorConfig changes text and class names, not enforcement.
  • data-b-validate-error-message and data-b-validate-message write with textContent, so those slots are text-only.
  • An AJAX form posts whatever the form contains. Validate the payload server-side before acting on it.

Secrets deserve the same directness:

  • Anything in the constructor's data is available to every expression and can end up in the DOM, in a prerendered HTML file or in a console log.
  • Attributes are public too. An API key in data-b-event-remote or in a payload attribute is readable by anyone who opens developer tools.
  • Browser requests carry cookies and headers, and their responses are visible to the user. Secrets belong on the server, behind an endpoint that does the privileged work.
  • Prerendered output is static HTML. Whatever was rendered at capture time is in the file, so render only what may be published.
